## Scanner contract and release implications

The backend expects a private Cloudflare service binding named **DOCUMENT_SCANNER** with a Fetcher-compatible fetch method.

1. Backend sends POST to the binding at https://document-scanner/scan with raw file bytes, Content-Type and X-Document-SHA256.
2. A successful response must be JSON with status = clean and sha256 equal to the request digest. Any other verdict rejects; transport failure never commits the object as reviewed.
3. The binding is given a 15-second deadline. Multipart intake is capped at 10 MiB + 128,000 bytes and 30 seconds. Upload clients allow 60 seconds; normal API calls retain 20-second deadlines.
4. Production readiness and production uploads reject if the binding is absent. Development prefilter-only acceptance is NOT a safe-file certification.
5. The provider must supply malware/active-content detection, robust parsing/decompression limits, isolation, operating-region/retention guarantees and versioned evidence. Approve and test that integration before launch.
6. Existing retained document objects and old chat rows require an approved retention/disposal process. This work does not delete that evidence or presume a legal retention period.

Legacy submissions without a content hash cannot be newly verified through the hardened interface. Parish staff must inspect and replace/reconcile legacy data through an approved process. Do not auto-mark those documents verified.

1. Approve production identity/MFA/ingress design and independently test it.
2. Choose and validate the document scanner, verified-email/recovery service, and notification/push provider. A change-password screen is not forgotten-password recovery.
3. Resolve conditional checklist applicability, staff-only versus self-service rescheduling/cancellation, and daily queue closure/expiry.
4. Extend bounded pagination/search beyond records and schedules to appointments, documents, queue, announcements and the access register; reduce the legacy dashboard payload. Manually verify multi-page UI flows and the staff records screen. Benchmark aggregate/conflict queries, mixed read/write/upload load, rate controls and password-hash cost on the chosen runtime. Current PBKDF2 cost migration is still outstanding.
5. Complete approved privacy notice, consent/retention/deletion workflows, historical-data review, purpose-based privileged access and record governance.
6. Run installed-device iOS/Android tests: secure storage failures, document permissions, hardware back/deep links, background/resume, keyboard and large text, slow/absent internet, upload interruption and retries.
7. Execute backup/restore, monitoring/alerting and incident-response drills. Re-run all security checks against isolated production-like infrastructure before handling real records.
8. Continue sustained development-runner testing after the runtime patch; reproduce or explain the historical connection failures and renderer warnings, including long sessions and sleep/resume. The passing short probes and transport fault injection do not close this gate.

These gates require additional implementation and/or owner/provider decisions. Do not label the system ready while they remain open.
